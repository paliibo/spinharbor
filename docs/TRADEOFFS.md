# Technical trade-offs and known limitations

## Deliberate trade-offs

| Decision | Why | Cost |
| --- | --- | --- |
| Modular monolith instead of microservices | One deployable, one transaction boundary around stake → outcome → payout, no distributed-transaction complexity. | Modules share a database; scaling is vertical first. |
| `BigInt` minor units + cached wallet balance | Exact arithmetic; O(1) balance reads; the journal remains the source of truth and is reconciled. | Two writes per movement; cache/journal drift would be a bug class (guarded by tests + job). |
| Row lock (`FOR UPDATE`) rather than optimistic versioning | Simplest correct way to serialise a player's financial operations under concurrency. | Requests for one player serialise; throughput per player is bounded (fine for a casino). |
| Idempotency keys generated by the client | Retries after network failures are safe without server-side de-duplication heuristics. | Clients must persist/reuse the key for a retry (the web client does per attempt). |
| In-process crash loop with server timers | Simple, server-authoritative, trivially testable by manipulating persisted state. | Single API instance; a second instance would run a second loop. A Redis-leased scheduler would be the next step. |
| Socket events published after commit via an in-process bus | No cross-module imports, no events for rolled-back work. | Not durable; a client that misses an event re-syncs from REST (wallet versions, crash snapshot). |
| Cookies (httpOnly) for the browser + Bearer for tools | XSS-safe tokens; Swagger/curl still work. | Needs same-site deployment or a proxy in production. |
| Zod contracts shared by API and web | Validation written once, Swagger generated, compile-time types on both ends. | Swagger schemas are JSON-Schema translations, not hand-curated. |
| Prisma 6 (not 7) and NestJS 11 (not 12) | Mature, well-documented versions; avoided breaking changes mid-build. | Not the newest majors. |
| Procedural SVG artwork | Zero third-party assets, consistent look, tiny bundle. | Less illustrative than painted art. |

## Known limitations (honest list)

- **Single instance.** The crash round loop and session reminders run in process memory. Horizontal scaling needs a leader election for the loop (and sticky sessions or a Redis adapter for Socket.IO).
- **No real money, KYC, AML or jurisdiction logic** – by design. Responsible-gaming features are a demonstration, not certified compliance infrastructure.
- **Limit cool-downs are immediate.** Real products delay the loosening of limits by 24 h; here it is immediate but audited.
- **External providers are stubs.** Nothing talks to a third party; enabling a stub is refused.
- **Tournaments** are not implemented (the module placeholder from the brief was dropped).
- **Container images / CI deploy** for the apps are not included; only Postgres/Redis run in Docker Compose. A GitHub Actions workflow runs lint, typecheck, build and the backend tests.
- **E2E coverage** focuses on the two mandated scenarios plus route/RBAC/bonus smoke tests; roulette and crash are verified by backend tests and manually, not by Playwright.
- **RTP/RNG** are simulation-grade (`node:crypto` CSPRNG, Monte Carlo estimates), not certified.
- **Session reminders** are based on socket connection time, not aggregated across devices.
- **Idempotency records** live in PostgreSQL with a 24 h TTL cleaned by a job; a Redis-backed store would be faster at scale.
- **Browser cookie auth across origins** assumes web and API on the same site (localhost); production would sit behind one domain or a reverse proxy.
